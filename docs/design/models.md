# 후보 모델 설계

상태: **후보**. 채택 전이다. 채택 여부와 시점은 `PLAN.md`(M3 · M4)와 `STATE.md`가 정한다. 이 문서는 "무엇을 만들 수 있고 왜 그렇게 만드는가"를 설명하는 참고 자료이고, 여기 적힌 수치(층 수, 차원, λ)는 출발점이지 결정이 아니다. 그림은 `docs/design/model-diagrams.html`(브라우저로 연다).

계보: 모델 A의 뼈대는 이전 프로젝트(EASEM v2)에서 만든 Transformer에서 왔다. 그 프로젝트의 결정은 승계하지 않으므로(`STATE.md` D4), 여기서는 구조를 처음부터 다시 설명하고 입력을 현재 경계에 대조했다.

## 0. 공통 전제

### 0.1 문제

EB-NeRD의 한 **impression**은 사용자 한 명에게 한 화면에 보인 후보 기사 목록(`article_ids_inview`, 보통 5–30개)이고, 그중 1개 이상을 클릭했다. 모델은 impression마다 후보별 점수를 내고, 점수 순으로 순위를 매긴다. 평가는 impression 단위 AUC(주), MRR, nDCG@5 · 10이다(`docs/data.md` "공식 지표"). 같은 화면 안의 후보끼리 비교하는 문제라, 후보를 독립적으로 채점하는 것보다 **후보 집합을 한꺼번에 보고 상대 평가하는 구조**가 유리하다. 아래 두 모델은 모두 그 구조(후보 집합 Transformer)를 쓴다.

### 0.2 입력 경계

입력은 `AGENTS.md` "2. 입력 경계"를 따른다. 핵심은 세 가지다. (1) test 파일에 있는 정보만, (2) 노출 시각 t보다 엄격히 이전의 정보만, (3) 세 split을 같은 코드로. 그 주의 클릭은 test에 없으므로 **클릭은 학습 목표(loss)로만 쓰고 입력으로는 쓰지 않는다.** 두 모델이 쓰는 입력을 경계에 대조한 표는 5절에 있다.

### 0.3 입력 묶음

두 모델이 공유하는 네 묶음이다.

| 묶음 | 내용 | 비고 |
|---|---|---|
| **impression 정보** | 노출 시각(하루 중 시각 등), 기기 종류 | 화면 하나에 1개 |
| **기사 정보** | category, topic(복수), sentiment 점수, 발행 후 경과 시간(t − `published_time`), 텍스트 벡터 | 후보와 개인 기록의 기사에 공통으로 쓴다. 텍스트 벡터는 모델 A가 공식 768D 벡터, 모델 B가 제목 · 부제 문장 임베딩 |
| **기간 내 인기** | 후보 기사가 t 이전 10분 · 60분 동안 **전체 사용자**의 impression에 후보로 등장한 횟수(노출 수)와, 그 횟수의 같은 화면 안 순위. 후보 내 최신 순위(발행 시각 기준) | BA 행(`STATE.md` D3)은 집계에서 뺀다. t와 같은 시각은 "이전"이 아니다 |
| **개인 기록 H21** | history 파일에 든 그 사용자의 직전 21일 클릭 기사(최근 ≤100개)와 각 클릭 시각 | test에도 history 파일이 있다. 같은 주 안에서는 사용자마다 고정이다 |

### 0.4 공통 뼈대: 후보 집합 Transformer

```
impression 정보 ──► impression 인코더 ──► I0 (128D 토큰 1개)
후보 i의 정보   ──► 후보 토큰 인코더  ──► Cᵢ (128D 토큰, 후보마다 1개)

[I0, C₁, …, Cₙ] ──► Transformer 인코더 (8층, 128D, head 4, 위치 정보 없음)
                ──► 출력층(Linear → 스칼라) ──► 후보별 점수 s₁…sₙ
```

- 위치 정보를 넣지 않는 이유: 화면 안 후보 순서(`article_ids_inview`의 순서)가 노출 위치를 뜻하는지 확인되지 않았고, 순서에 의존하면 test에서 순서 분포가 다를 때 깨진다. 후보는 집합으로 다룬다.
- I0를 함께 넣는 이유: "이 화면은 아침 모바일 사용자의 것"처럼 모든 후보에 공통인 문맥을 후보 토큰들이 attention으로 참조하게 한다.
- 크기(8층 128D)는 2024 우승팀의 단일 Transformer와 같다(4절). 파라미터는 약 1–2M으로 작다.

### 0.5 Loss

`BCE + λ · ListNet`, λ = 0.1 출발.

- **BCE**: 후보별 점수에 sigmoid를 씌워 클릭 여부(0/1)와 비교한다. 절대적인 클릭 확률을 배운다.
- **ListNet**: 한 impression 안에서 점수에 softmax를 씌운 분포와, 라벨을 정규화한 분포(클릭한 후보에 균등) 사이의 cross-entropy. "같은 화면 안에서 클릭한 것이 위에 오게" 하는 listwise 항이라 AUC · nDCG와 방향이 맞는다.
- 라벨(`article_ids_clicked`)은 이 두 항에만 들어간다. 입력 어디에도 들어가지 않는다.

## 1. 모델 A — 공식 768D 기사 벡터를 쓰는 기준 Transformer

### 1.1 한 문장

기사 메타와 공식 768D 내용 벡터로 기사 표현을 만들고, 후보가 자기 개인 기록(H21)을 cross-attention으로 읽어 개인화한 뒤, 기간 내 인기 숫자와 합쳐 후보 집합 Transformer로 채점한다.

### 1.2 구조

```
①② 기사 표현 (후보 · 기록 공유)
    category · topic(평균) · sentiment 임베딩  ─┐
    공식 768D 벡터 → Linear(768→128) 어댑터     ─┴─ add → LayerNorm → e (128D)

④ impression 인코더
    시각 · 기기 → 각각 128D 인코딩(숫자는 sinusoidal, 기기는 임베딩) → Linear(256→128) → I0

③ 후보 문맥 인코더
    [e_cand (128D), 문맥 숫자 5개 × sinusoidal 128D] → Linear(768→128) → C0
    문맥 숫자 = 후보 내 최신 순위, 10분 노출 수, 10분 노출 순위, 60분 노출 수, 60분 노출 순위

⑦ 기록 토큰
    기록 기사 각각의 e (①② 공유) → H21 토큰들 (≤100개, 128D)

⑧–⑩ 후보 → 기록 cross-attention
    Q = C0, K · V = H21 토큰, head 4 → P21 (128D)
    후보별 gate α21 = sigmoid(Linear([C0, P21]))  (기록이 없거나 맞지 않으면 0에 가깝게)

융합 (파라미터 없음)
    C1 = C0 + α21 · P21

⑪ 후보 집합 Transformer: [I0, C1₁, …, C1ₙ] → 8층 128D head 4
⑫ 출력층 → 후보별 점수
loss: BCE + 0.1 · ListNet
```

### 1.3 왜 이렇게 만드나

- **기사 표현을 후보와 기록이 공유한다.** "후보가 기록의 어떤 기사와 닮았나"를 attention으로 재려면 둘이 같은 공간에 있어야 한다.
- **개인 기록을 cross-attention으로 읽는다.** 2024 우승팀은 개인 기록을 후보별 숫자 요약(기록에 있는가, topic 겹침 순위 등)으로만 썼다(4절). 모델 A는 후보가 기록 기사 하나하나를 직접 보게 해서, 요약으로는 잃는 "어느 관심사와 맞았는가"를 쓸 수 있게 한다. 이것이 우승팀 구조와의 핵심 차이이고, 그 효과를 1.5절의 arm B − A로 잰다.
- **gate를 둔다.** 21일 기록이 없는 사용자(history에 없음)나 후보와 전혀 안 맞는 기록에서는 P21이 소음이다. gate가 0으로 닫히면 C1 = C0로 돌아간다.
- **인기 숫자는 후보 토큰에 직접 넣는다.** 노출 수는 편집진의 배치(노출 정책)를 담는 강한 신호다. 우승팀의 설정 000 → 001 차이(0.77 → 0.87)가 그 크기를 보여 준다(4절). 단 우승팀의 "이 사용자에게 이번 주 이미 노출됐는가" 피처는 모델 A에 없다. 그 피처는 경계 안이지만(t 이전 노출) 첫 실험에서는 뺀다.

### 1.4 알려진 위험

- **768D 벡터가 기사 ID처럼 외워질 수 있다.** 기사마다 고유한 고차원 벡터는 어댑터를 거쳐도 "이 기사"를 특정할 수 있어, train 주의 기사에 과적합하고 test 주의 새 기사에 일반화하지 못할 수 있다. 이전 프로젝트의 한 실험에서 원본 768D 벡터를 후보 토큰에 직접 넣었더니 기록이 적은(sparse) 사용자에서 nDCG@10이 0.032 떨어진 관찰이 있다. 이 위험이 모델 B를 제안하는 이유다.
- **공식 768D 벡터가 어떤 텍스트로 만들어졌는지 확인되지 않았다**(`docs/data.md`). 본문을 포함하는지에 따라 담긴 정보가 다르다.
- **기록 토큰에 클릭 시점 정보가 없다.** 3주 전 클릭과 어제 클릭이 같은 무게다. 모델 B에서 시간 임베딩으로 보완한다.

### 1.5 첫 실험: 입력을 하나씩 더하는 세 arm

구조와 학습 설정은 같고 입력만 켜고 끈다.

| arm | 기사 정보 · impression | 개인 기록 H21 | 기간 내 인기 | 읽는 것 |
|---|---|---|---|---|
| **A** | 켜짐 | 꺼짐 | 꺼짐 | 기사 정보만의 실력. C1 = C0, 문맥 숫자는 최신 순위 하나 |
| **B** | 켜짐 | 켜짐 | 꺼짐 | **B − A**: 개인화의 순수 기여 |
| **C** | 켜짐 | 켜짐 | 켜짐 | **C − B**: 노출 정책 정보가 더하는 몫 |

- arm마다 seed 3개, 합계 9회. 공식 validation 점수로 비교한다. test 점수는 선택에 쓰지 않는다.
- 참고 수준: 우승팀 설정 000(인기 없음)이 0.7699, 001(과거 인기 포함)이 0.8680. A · B는 000, C는 001과 정보 수준이 가깝다. 피처와 학습 방식이 달라 직접 비교 기준은 아니다.
- 인기와 개인 기록의 상호작용이 궁금해지면 arm X(기사 + 인기, 기록 없음)만 추가한다. 2×2 전체 설계는 하지 않는다.

## 2. 모델 B — 제목 · 부제 임베딩을 관계 경로에만 쓰는 모델

### 2.1 한 문장

덴마크어 문장 인코더로 만든 제목 · 부제 임베딩을 **후보와 개인 기록을 비교하는 cross-attention 안에서만** 쓰고, 최종 Transformer에는 그 비교의 **결과**(기록 쪽 가중합 벡터 o와 유사도 숫자)만 넘긴다. 후보 자신의 텍스트 벡터는 최종 Transformer에 들어가지 않는다.

### 2.2 왜

- 1.4의 위험을 구조로 막는다. 후보 토큰에 후보 고유 벡터가 없으면 모델이 "이 기사"를 외울 길이 없다.
- 문장 의미 공간에서는 비슷한 기사가 가까이 놓이므로, 학습 때 못 본 기사(test 주의 새 기사, BA의 250개 기사)도 과거 클릭과 의미가 가까우면 점수를 받는다.
- 제한하는 것은 **기사마다 고유한 고차원 벡터**(문장 임베딩, 공식 768D)뿐이다. category · topic · sentiment는 값의 종류가 적어 기사를 특정하지 못하므로 최종 Transformer에 직접 넣는다.

### 2.3 텍스트 임베딩

- 입력 문자열: `title + ". " + subtitle`. subtitle이 없으면 title만 쓰고 그 비율을 보고한다.
- 인코더는 **고정**한다(미세조정 없음). raw BERT의 CLS가 아니라 문장 의미용으로 학습된 인코더를 쓴다.
- 후보 인코더(모델 ID · license 확인 필요): `intfloat/multilingual-e5-base`(입력에 `passage: ` 접두어), `sentence-transformers/paraphrase-multilingual-mpnet-base-v2`, 덴마크어 특화 문장 인코더 1개. 어느 것을 쓸지는 3절의 절차로 고른다.
- 최대 128 token, L2 정규화, fp16. 125,541개 기사를 한 번만 인코딩해 article_id 대응표와 함께 `$EBNERD_DATA_ROOT` 아래에 저장한다(로컬 RTX 4060 Ti에서 인코더당 수 분).
- 외부 통신은 모델 다운로드뿐이다. 기사 텍스트는 로컬에서만 처리한다. Hugging Face cache도 `$EBNERD_DATA_ROOT` 아래에 둔다.
- 제목 · 부제는 최종 snapshot 값이다(`docs/limitations.md` 1). 공식 배포에 다른 BERT 계열 기사 임베딩이 있는지, 있다면 어떤 텍스트로 만들었는지는 확인되지 않았다.

### 2.4 구조

```
공유 기사 인코더 (후보 · 기록 같은 가중치)
    텍스트 임베딩(고정) → Linear → 64D
    category 임베딩, topic 임베딩 평균, sentiment
    concat → Linear → LayerNorm → e (128D)
    m = 텍스트를 뺀 메타 임베딩만 (후보 토큰 인코더로 따로 보낸다)

기록 토큰 (H21, ≤100개)
    e_hist + 시간 구간 임베딩 (클릭 후 경과 시간의 log 구간, 같은 기사 클릭 수 구간; 각 128D)
    + 학습되는 null 토큰 1개 (기록이 없거나 맞는 기록이 없을 때 attention이 갈 곳)

후보 → 기록 cross-attention
    Q = e_cand, K · V = 기록 토큰, head 4, 128D
    [실험] 시간을 attention 점수에 더하는 bias: score_i += f(경과 시간_i)
    o = Σ wᵢ · Vᵢ

관계 출력 (벡터 + 숫자)
    o → Linear → 64D
    cos(o, e_cand), 최대 유사도, head별 유사도, attention 엔트로피

후보 토큰 인코더
    [o 투영 64D, 관계 숫자, m, 기간 내 인기 숫자] → concat → MLP → C (128D)
    ✕ e_cand와 o ⊙ e_cand는 넣지 않는다

impression 인코더: 시각 · 기기 · H21 숫자 요약(길이, 마지막 클릭 이후 시간, 기록 없음 플래그) → I0
후보 집합 Transformer: [I0, C₁, …, Cₙ] → 8층 128D head 4 → 출력층 → 점수
loss: BCE + ListNet
```

모델 A와의 차이: A의 후보 문맥 인코더(③)와 융합(C1 = C0 + α·P21)이 후보 토큰 인코더 하나로 바뀐다. 텍스트 벡터는 후보 토큰에 직접 들어가지 않고, cross-attention 결과는 gate로 더하는 대신 관계 출력으로 합친다.

### 2.5 설계 규칙

1. **매칭은 내용으로, 인기는 그 뒤에.** Q · K에는 텍스트와 메타로 만든 e만 넣는다. 노출 수 · 순위는 후보 토큰 인코더에서 합친다. 기록 기사에는 인기와 같은 뜻의 값이 없어서 Q에 넣으면 매칭이 흐려진다. "많이 노출된 기사를 고르는" 효과는 최종 Transformer가 직접 배운다.
2. **후보와 기록은 같은 인코더를 쓴다.** 같은 공간에 있어야 "의미가 가깝다"는 비교가 성립한다.
3. **메타는 이어 붙인 뒤 줄인다.** 고정된 텍스트 64D와 학습되는 메타 임베딩은 크기와 분포가 달라, 그냥 더하지 않고 concat → Linear → LayerNorm으로 합친다.
4. **기록 쪽 시간은 차원을 맞춰 더한다.** 스칼라를 log 구간 임베딩(128D)으로 바꾼 뒤 e_hist에 더한다(Transformer 위치 인코딩, BST의 시간 임베딩과 같은 방식). 더하는 쪽도 학습되므로 모델이 내용과 시간을 겹치지 않는 방향에 나눠 담는다.
5. **빈 기록용 null 토큰을 둔다.** "기록 없음" 플래그와 함께 "기록이 없음"과 "기록은 있는데 안 맞음"을 구분한다.
6. **o는 넘기고, 후보 벡터는 넘기지 않는다.** o는 기록 쪽 가중합이라 투영해 넘겨도 암기 위험이 작고, 숫자만 넘길 때보다 표현력이 크다. `e_cand`, `o ⊙ e_cand`는 후보 신원을 직접 실어 나르므로 막는다.
7. **인코더는 고정한다.**

참고: 후보–기록 attention의 일반적인 형태는 DIN 계열(가중치 = `MLP([q, h, q−h, q⊙h])`), BST 계열(Q · K · V multi-head cross-attention), 뉴스 추천 계열(NRMS · NAML: 기록만으로 사용자 벡터를 만든 뒤 후보와 내적)이다. 모델 B는 BST 계열을 쓰고, 데이터가 적어 불안정하면 DIN 계열로 바꾼다.

### 2.6 o가 담는 정보

o는 "이 후보와 관련된, 이 사용자의 과거 관심사 요약"이다. 21일 클릭이 축구 10 · 정치 5 · 날씨 2인 사용자라면, 축구 후보에는 o가 축구 클릭들의 가중 평균에 가깝고, 정치 후보에는 정치 쪽으로 가며, 아무것과도 맞지 않는 후보에는 attention이 null 토큰으로 가서 "관련 관심사 없음"이 된다.

| 담기를 기대하는 정보 | 어디서 오나 | 유사도 숫자만으로는 |
|---|---|---|
| 어느 관심사와 맞았나 | attention이 고른 기록 기사들의 내용 | "얼마나"만 알고 "무엇과"는 모른다. 습관적 관심사와 우연한 관심사의 클릭률 차이를 배울 수 없다 |
| 맞은 클릭의 시점 · 반복 | V에 더한 시간 · 클릭 수 임베딩 | 어제 세 번 읽은 주제와 3주 전 한 번 본 주제를 구분하기 어렵다 |
| 맞은 기록의 성격 | V 안의 category · sentiment | "부정적 논조의 사건 기사에 반응해 왔다" 같은 정보가 사라진다 |
| 매칭이 한쪽에 몰렸나 | o의 크기(한 묶음에 몰리면 크고, 퍼지면 상쇄돼 작아진다) | 엔트로피로 일부만 전달된다 |
| 같은 화면 후보끼리의 비교 | 후보마다 생기는 o를 후보 집합 Transformer가 견준다 | 핵심 관심사와 주변 관심사에 닿는 후보를 구분하기 어렵다 |

- 담기면 안 되는 것: 후보 기사 자체의 신원. o는 항상 사용자 기록 벡터들의 볼록 결합이고, 후보는 섞는 비율 wᵢ에만 영향을 준다. 기록이 1개뿐인 사용자는 어떤 후보가 와도 o가 거의 같다.
- 허용되는 누출: attention이 한 기록에 날카롭게 몰려 o가 비슷한 과거 기사 하나에 가까워지는 경우. 주제 수준 정보라 비슷한 새 기사에도 통한다.
- 남는 위험: 후보와 같은 기사가 21일 기록에 이미 있으면 o가 그 기사 벡터와 거의 같아질 수 있다. (a) 그 기록을 attention에서 빼고 "기록에 있음 · 클릭 수" 숫자로만 넘기는 방식과 (b) 그대로 두는 방식을 비교한다.
- 확인: o만으로 후보 category를 맞히는 probe는 잘 맞아야 하고, 후보 기사 ID probe는 거의 못 맞혀야 한다. 기록을 다른 사용자 것으로 바꿔 넣었을 때 떨어지는 폭이 개인화 신호의 크기다.

## 3. 텍스트 인코더 선택 — 학습 없는 유사도 단독 AUC

모델 B의 텍스트 출처와 인코더를 고르는 절차다. 학습이 없어 싸고, 결과는 Plan M3의 "history 피처(공식 벡터 유사도)"에도 그대로 쓰인다.

- **출처**: (a) 공식 768D 벡터, (b) 2.3의 문장 인코더 2–3종. 비교 기준 (c) 텍스트 없이 만든 겹침 피처(후보와 같은 category인 기록 비율, 후보 topic이 기록에 나온 비율).
- **유사도 피처**(후보 1개 × 그 사용자의 21일 기록 ≤100개, 후보와 같은 기사는 제외 — 같은 기사 재클릭은 "기록에 있음" 피처가 담당): cos 유사도로 `sim_max`(최대), `sim_mean`(평균), `sim_top5`(상위 5개 평균), `sim_recent`(경과 시간 반감기 72시간 가중 평균), `sim_centroid`(기록 평균 벡터와의 cos), `sim_n`(비교한 기록 수). 기록이 없으면 NULL이고 그 impression은 AUC에서 빼고 수를 보고한다.
- **계산**: 각 피처 값을 그대로 점수로 써서 validation의 impression AUC를 낸다. (사용자, 후보 기사) 중복 쌍을 없앤 뒤 GPU fp16으로 계산한다.
- **대조**: 출처마다 article → embedding 대응을 무작위로 섞은 shuffle 버전의 AUC.
- **불확실성**: user 단위 cluster bootstrap 200회(seed 고정)로 95% CI.
- **선택 규칙(제안)**: `sim_max` 또는 `sim_recent`의 AUC가 가장 높은 출처를 고른다. 단 같은 출처의 shuffle보다 CI 하한 > 0으로 높아야 한다. 고른 인코더 1개와 공식 768D를 2.7의 텍스트 출처 비교에 쓴다. **어떤 출처도 shuffle을 넘지 못하면 모델 B를 보류하고 그 사실을 기록한다.**
- 예상 비용(실측 아님): 인코더당 인코딩 5–15분, 유사도 출처당 20–60분, AUC 수 분. 합계 2–5시간.

## 4. 참고: 2024 우승팀 단일 Transformer(v1170)

구조를 비교할 기준점이다. 공개 코드의 입력 목록을 옮겼다.

- **구조**: impression 피처 → (숫자는 sinusoidal 128D, 기기는 임베딩) → concat → Linear → BN → ReLU → I0. 후보 피처 → (숫자 sinusoidal 128D, topic · category 임베딩과 학습되는 유사도) → concat → Dropout → Linear → BN → ReLU → 후보 토큰 128D. [I0, 후보들] → 8층 128D head 4 Transformer → 출력층. loss BCE만. 사용자당 impression 2개 샘플링, AdamW.
- **개인 기록**: 순서대로 읽지 않는다. 후보마다 숫자 요약(기록에서 클릭했는가 · 횟수 · 순서 · 시간, topic · category 겹침 순위, 임베딩 유사도)으로만 들어간다. 768D 벡터는 쓰지 않았다.
- **설정별 AUC**(보고된 값. validation인지 hidden test인지는 확인 필요):

| 설정 | 켜지는 피처 | AUC |
|---|---|---|
| 000 | impression 기본 + 기록 요약 + 기사 자체 + 기록 매칭 | 0.7699 |
| 001 | 위 + 이번 주 **과거** 노출(이 사용자에게 이미 노출됐는가, 전체 최근 인기) | 0.8680 |
